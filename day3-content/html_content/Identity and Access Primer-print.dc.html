Group membership
Decides who is in each group. Since permissions are granted to groups, this is where access is actually won or lost.
Assigned: group owners add and remove members by hand.
Dynamic: a rule adds members automatically, e.g. user.department -eq "Finance". Needs Entra ID P1.
Security groups are for access; Microsoft 365 groups are for collaboration.
Nesting: Azure RBAC honours nested groups. The Databricks SCIM connector syncs direct members only; automatic identity management supports nesting.
Access reviews (P2) ask owners to recertify members on a schedule.
App registrations & SP credentials
An app registration defines the application and its client ID. Its service principal (listed under Enterprise applications) is the instance in your tenant that receives permissions.
Client secret: a password with an expiry (up to 24 months). Store it in Key Vault and rotate it.
Certificate: stronger than a secret, and the private key never leaves your vault.
Federated credential: trusts a token from GitHub Actions or Azure DevOps. No secret exists at all. Preferred for CI/CD.

MFA & Conditional Access
Policies evaluated at every sign-in: if these conditions, then require or block. They protect the Azure portal and Databricks alike.
Conditions: user or group, target app (e.g. AzureDatabricks), location, device, sign-in risk.
Controls: require MFA, a compliant device, or block access.
Example: all users reaching Databricks must use MFA from a managed device.
Non-humans: service principals need Workload ID policies; managed identities aren't subject to Conditional Access.

03

How identities get from Entra ID into Databricks

Databricks doesn't create its own users. It copies identities from Entra ID into the Databricks account, and workspaces then pick them up through identity federation. You create and remove people, groups and service principals only in Entra ID.

THE FLOW
1 · ENTRA ID Source of truth Admin adds Marcus to grp-analysts-finance.
2 · SYNC Automatic identity management or SCIM The change is carried to Databricks. The two methods are compared below.
3 · DATABRICKS ACCOUNT Account-level identity Marcus and the group now exist once, for every workspace in the account.
4 · WORKSPACE + UC Assignment & grants The group is assigned to dbw-prod and already holds its UC grants, so Marcus has access with no extra steps.
Automatic identity management
RECOMMENDED
Databricks reads Entra ID directly. You turn it on once in the account console, and there's no enterprise app to set up.
How: on demand. An identity is added when someone searches for it to grant access, or when a user first signs in.
Scope: every user, group and SP in the tenant can be found, so nothing has to be assigned up front.
Nested groups: supported. Membership is resolved from Entra ID when it's needed.
Managed identities can be added as service principals.
SCIM provisioning
An Entra ID enterprise application (the Azure Databricks SCIM Provisioning Connector) pushes identities into the account on a schedule.
How: Entra ID's provisioning service runs about every 40 minutes, authenticating with a Databricks account SCIM token.
Scope: only users and groups assigned to the enterprise app are synced.
Nested groups: not flattened. Only direct members are synced.
Use when you need an explicit allow-list of who exists in Databricks.
WHAT HAPPENS WHEN ENTRA ID CHANGES
IN ENTRA ID

New app registration for a pipeline
Add the SP to the account, then assign it to a workspace and grant it privileges
Avoid local workspace users and groups
Identities created by hand inside a single workspace don't come from Entra ID, can't hold Unity Catalog grants properly, and are missed when people leave. Manage identities in Entra ID and at the account level only.
